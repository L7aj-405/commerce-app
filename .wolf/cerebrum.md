## User Preferences

- **UI Design system**: Uses utility classes defined in `app.css` (`@layer components`): `.card`, `.btn`, `.btn-primary`, `.btn-secondary`, `.btn-danger`, `.btn-success`, `.btn-ghost`, `.input`, `.label`, `.badge`, `.badge-{color}`, `.table-container`, `.table-th`, `.table-td`, `.table-row`, `.page-title`, `.page-subtitle`, `.filter-bar`. Always use these instead of raw Tailwind strings.
- **Dark mode**: Class-based (`darkMode: 'class'` in tailwind). Toggle managed by Alpine.js `x-data` on `<body>` + inline `<head>` script to prevent FOUC. Button dispatches via `darkMode = !darkMode`.
- **Icons**: Heroicons outline SVG inline (viewBox="0 0 24 24", stroke-width="1.7"), never emojis, never external icon fonts.
- **Font**: Inter from Bunny Fonts (switched from Figtree).
- **Empty states**: Use dedicated card with centered SVG icon + title + subtitle, never just "No X found" text.
- **Action buttons in tables**: Use `.btn-icon` with SVG icons + `sr-only` labels for accessibility.

## Key Learnings

- **Migrations were squashed to one clean create-per-table set (2026-07-26):** The old 61-file history (initial creates + a long tail of ALTERs) was consolidated into **34 `create_*` migrations under `database/migrations/`, one per table**, each holding the FINAL schema. Timestamps encode FK dependency order (core `0001_01_01_*`; then stores→children; `store_roles` deliberately precedes `store_members`/`store_invitations` because they FK it). Rules baked in for future migrations: **(1) evolving value lists are `string`/VARCHAR, not native ENUM** — `orders`/`pos_orders.fulfillment_status` (32), `inventory_adjustments.source` (32); the app enums (`FulfillmentStatus`, `CustomerType`, …) validate. **(2) Native ENUM is fine only for closed sets** (`sync_logs.direction/action`, `factures.status`, `products.type/status`, POS payment methods) — but remember MySQL ENUM `MODIFY` is a raw `DB::statement` that must be guarded `if (driver === mysql)` or it fatals on the SQLite test DB. **(3) ULID everywhere = `char(26)`**; `$table->ulid()`, `$table->char(...,26)`, and morphs via `nullableUlidMorphs()` (spatie's activity_log needs char(26) morph ids, NOT its default unsignedBigInteger). **(4) ground truth** for a table's final columns = `SHOW CREATE TABLE` on a fully-migrated DB, extracted here via a throwaway scratch DB (`saas_squash_tmp`) driven by `~/.config/herd/bin/php84.bat artisan` with `$env:DB_DATABASE` overridden — never the real `saas_commerce` dev DB. Verify any migration rewrite with BOTH `migrate:fresh` on MySQL and the Pest suite on SQLite.
- **Order lifecycle foundation (Phase 3, 2026-07-24):** Full design lives at `docs/order-lifecycle.md` (read it before touching returns/fulfillment). `App\Enums\FulfillmentStatus` grew from 5 to 10 states — `pending`(→ relabelled "Pending confirmation") → `confirmed` → `in_progress`("Processing") → `ready_for_delivery` → `delivered` → `completed`, plus `cancelled` and the return flow `returned` → `under_inspection` → `return_completed`. Cancellation is legal only BEFORE dispatch; after that the exit is `returned`. New enum helpers: `phase()` ('confirmation'|'fulfillment'|'closed'|'returns' — drives the board's department tabs), `isReturnFlow()`, `requiresReason()` (cancelled+returned), `permission(?self $from)` (takes the CURRENT status because cancelling belongs to whichever department owns the current phase). **The enum answers "is this edge legal" only** — preconditions that depend on other rows (a return may only close once every line has a condition, see `OrderReturn::isFullyDispositioned()`) live in the service layer deliberately, so the UI renders the button disabled instead of hiding it.
- **Internal delivery agent dashboard + COD (Phase 3, 2026-07-25):** A driver's own mobile-first queue at `/dashboard/my-deliveries` (`DeliveryController`, `Pages/Dashboard/Delivery/MyDeliveries.jsx`), separate from the manager-facing `DepartmentController` dispatch board. New permission **`orders.deliver`** + non-locked **Delivery agent** role holding ONLY `orders.deliver` (no `orders.view` — a driver never sees the department boards; `orders.deliver` alone grants dashboard access since it's not `pos.access`, so `getActiveStore` resolves + `can_dashboard` passes). Every DeliveryController action is scoped to `OrderShipment where(store, agent_id=self, status=dispatched)` via `resolveOwn()` → a driver acting on another's parcel 404s. COD: migration `2026_07_25_130000` added `order_shipments.cod_amount` (expected, set at `DispatchService::assign()` from `expectedCod()` = PosOrder unpaid balance `total_amount - amount_paid`, or Order full total) + `cod_collected` (nullable, entered on delivery). `markDelivered(shipment, actor, ?codCollected)` stores collected cash only when `cod_amount > 0` (prepaid stays null). `agentQueue()` + `agentReconciliation()` (outstanding/collected_today/delivered_today/in_queue) back the mobile UI. Failed delivery → `markFailed` → Returned (reverse logistics, no stock move) — driver failure-reason values (`refused`/`damaged_in_transit` align to `OrderReturn::reasons()`; others become 'other'). UI: gradient reconciliation header, big-tap cards with `tel:` call + Google Maps (`https://www.google.com/maps/search/?api=1&query=<enc>`) quick links, two bottom sheets (deliver w/ COD input prefilled, fail w/ reason radios). **BUGFIX same commit:** the dispatch board's internal-agent picklist was `workload(store,'orders.dispatch',...)` (listed fellow dispatchers) — corrected to `'orders.deliver'` so dispatchers assign to actual drivers. Sidebar "My deliveries" gated `orders.deliver`. Tests: `tests/Feature/Orders/DeliveryAgentTest.php` (12).
- **Driver detection is ROLE-FIRST + component isolated (2026-07-25, hardening):** The confine/redirect logic was correct but `isDeliveryOnlyAgent()` originally keyed only on `orders.deliver && !orders.view`, which silently fails if the driver's role was given `orders.view` or you test as the store OWNER (owners are privileged → always manager). Hardened: it now returns true FIRST when the assigned `StoreRole->slug === User::DELIVERY_AGENT_ROLE` ('delivery-agent', = `Str::slug('Delivery agent')`) — assigning the seeded "Delivery agent" role is the reliable switch even if that role was tweaked to include extra perms; else falls back to `orders.deliver && !orders.view && !orders.manage`. Owners/super-admins are NEVER drivers (privileged) — to see the driver UI you MUST use a member account holding the Delivery agent role, not the owner. Defense-in-depth: `DashboardController@index` itself now `redirect('/dashboard/my-deliveries')` for a driver (belt-and-suspenders on top of the `confine_driver` middleware). Component ISOLATED out of the manager folder: `Pages/Dashboard/Delivery/MyDeliveries.jsx` → **`Pages/Delivery/DeliveryAgentView.jsx`** (export renamed to `DeliveryAgentView`); `DeliveryController` renders `'Delivery/DeliveryAgentView'`. Inertia has NO global persistent layout (`app.jsx` just resolves the page), so a page's own layout wins — DeliveryAgentView wraps `DeliveryAgentLayout` (standalone: only ThemeToggle + ToastNotification, zero manager chrome). Tests: 19 in `DeliveryAgentTest.php` incl. role-slug confinement surviving an added `orders.view`.
- **Delivery driver is REDIRECTED + CONFINED, not just re-skinned (2026-07-25):** The standalone layout alone was insufficient — a delivery agent's coarse dashboard access still let them (a) get redirected to `/dashboard` (manager) on login and (b) navigate to manager pages. Fixed with role-based routing keyed off **`User::isDeliveryOnlyAgent(?Store)`** = holds `orders.deliver` AND NOT `orders.view` AND not privileged owner/super-admin (a pure driver; owners/dispatchers/managers all return false). Two enforcement points: (1) `AppServiceProvider` Fortify `LoginResponse` redirects such users to `/dashboard/my-deliveries` (hard redirect, NOT `intended()` which could be a stale manager URL); (2) `App\Http\Middleware\ConfineDeliveryAgent` (alias `confine_driver`, added to the dashboard route group's middleware AFTER `can_dashboard`) redirects a driver to `dashboard.deliveries.index` for ANY dashboard route whose name doesn't start with `dashboard.deliveries.`. GOTCHA: this changes a driver hitting a manager page from **403 → 302-redirect** (confinement runs before the route's `perm:` middleware) — a test asserting 403 for that case had to flip to `assertRedirect`. Stats pill "N left" now lives in the `DeliveryAgentLayout` header (`pending` prop). Tests in `DeliveryAgentTest.php` (18 total): helper truth table, login→my-deliveries redirect, manager-page→my-deliveries redirect, driver can reach own view, manager NOT confined.

It has two tabs — **Pending** (live queue, action cards) and **History** (read-only delivered/failed). History cards show a delivered/failed chip + collected cash or failure-reason label. `ThemeToggle`/`ToastNotification` are standalone components reused outside SaasLayout — safe to drop into any custom layout. Reason: a driver on a phone must not see the manager dashboard.
- **Department dashboards (Phase 3, 2026-07-24):** Four dedicated per-team work queues at `/dashboard/departments/{confirmation,packing,dispatch}` + the existing `/dashboard/orders/returns`, all served by `DepartmentController`. They do NOT replace `/dashboard/orders/manage` — that stays the cross-department overview; a department page shows one team only the orders it can act on. **`App\Support\DepartmentRegistry`** is the single source of truth (key/phase/label/permission/href/icon); `visibleTo(User,Store)` returns what the viewer may work in, and super admins + store owners get all four for free via `isPrivilegedFor()` (no special case) while `orders.manage` also opens everything. Queues are **FIFO (`oldest()`)**, unlike the recency-sorted board. Frontend: `Hooks/useQueue.js` (search/scope/source/selection/busy — selection stored as a KEY not an object so it can't go stale; nothing copied into state) + `Components/Departments/{DepartmentNav,QueueParts}.jsx` (StatTiles, SourceBadge, QueueToolbar, AgentWorkload, EmptyQueue, ReasonDialog, fmtMoney/timeAgo/ageTone). Packing's item checklist is deliberately LOCAL throwaway state — a picker's scratchpad, not a record; the persisted outcome is the status move. `ageTone()` colours waiting time green<1h / amber<4h / red beyond.
- **Delivery is now its own phase (2026-07-24):** `FulfillmentStatus::phase()` split `fulfillment` into `fulfillment` (Confirmed, InProgress) and **`delivery`** (ReadyForDelivery, Delivered). Packing ends at ReadyForDelivery; from there the order belongs to logistics. `Delivered`/`Completed` now require **`orders.dispatch`** (new permission) instead of `orders.fulfil`, and cancelling from the delivery phase also maps to `orders.dispatch`. New **Dispatcher** role = `orders.view`, `orders.dispatch`, `orders.return` (a refused delivery is flagged from the dispatch board, not the warehouse). NOTE: any test asserting the set of phases must include `delivery` — this broke `OrderLifecycleFoundationTest` when the split landed.

- **`order_shipments` — the dispatch leg (2026-07-24):** Polymorphic like `order_returns` (`shippable_type/id` = Order|PosOrder), `reference` SHP-YYYYMMDD-0001 unique per store, `carrier_type` courier|internal, `carrier_name`/`tracking_number`/`tracking_url` for couriers, `agent_id` for internal riders, `manifest_reference` (a plain string batch label — a manifest has no attributes of its own yet), status pending|dispatched|delivered|failed. **Deliberately NOT folded into `bon_de_livraisons`** — that is a POS-only printable delivery-note document with its own status vocabulary; overloading it would tie two unrelated features together. `DispatchService::assign()` is idempotent per order (updates the in-flight shipment rather than creating a second); `markDelivered()` advances the order to Delivered; `markFailed()` routes it to Returned so the goods get inspected — **no stock moves on the dispatch board at all**.
- **Order assignment (2026-07-24):** `orders.assigned_to` + `assigned_at` on BOTH `orders` and `pos_orders` (nullable FK to users) — an order has at most one owner at a time, so a pointer beats an assignments table, and who moved it is already in the activity log. `OrderAssignmentService` does `takeNext(store,user,phase)` (claims the longest-waiting unassigned order in a phase), `claim()` (throws ValidationException if someone else got there first), `release()`, and `workload()` which powers the "active agents / queue distribution" widget — it lists every member with the phase's permission PLUS the store owner, with their current assigned count. Every claim is a locked read-then-write: checking "is it free?" outside a lock is exactly the race this prevents.
- **Order board departments + returns UI (Phase 3, 2026-07-24):** `Manage.jsx` now has a **department tab strip** above the source tabs. A "department" is just `perm + a set of FulfillmentStatus::phase() values` — `DEPARTMENTS` = All open / Confirmation (`orders.confirm`) / Fulfillment (`orders.fulfil`) / Returns (`orders.inspect`) / Closed, filtered by a local `can()` built from `usePage().props.auth.permissions` (SaasLayout's own `can` is NOT exported — rebuild it in the page). The active tab picks `visibleColumns` out of the 10-entry `COLUMNS` array, so a 10-status workflow never renders 10 Kanban lanes; `filtered` also drops orders outside those columns, which is why `counts.bySource` is computed department-aware (otherwise the tab tallies disagree with the board). Lane-count → grid class goes through a `GRID_COLS` literal map because Tailwind cannot see interpolated class names. **`ReasonModal`** intercepts any transition whose `requires_reason` is true (server-supplied, NOT re-derived in JS): a return picks from `RETURN_REASONS` (mirrors `OrderReturn::reasons()`, `other` reveals a textarea) and a cancellation is free text. Drawer action buttons are hidden when `!can(t.permission) && !can('orders.manage')` — the server re-checks, this only avoids offering a guaranteed 403. New pages `Pages/Dashboard/Orders/Returns/{Index,Inspect}.jsx`; Inspect keeps local `draft` verdicts keyed by item id, disables (never hides) "Close return" while `pending > 0 || dirty` to mirror the server rule, and shows a `Lock` chip on lines where `locked` (i.e. `stock_ledger_id` already set). `StatusBadge` gained `fulfillment` values for the 5 new states plus two new type maps: `return` (awaiting_inspection|inspecting|closed) and `condition` (resellable|damaged|missing). Sidebar gained a Returns item gated on `orders.inspect`.
- **`OrderPresenter::transitions()` emits `requires_reason` + `permission` per transition, and `phase` on the row.** The UI must never re-derive which moves need justifying or who may make them — both come from the enum via the presenter. Adding a field here is the way to teach the React board something new about the workflow.
- **Three seeded department roles (2026-07-24):** `PermissionCatalog::defaultRoles()` now also seeds **Confirmation agent** (`orders.view`, `orders.confirm`), **Warehouse** (`orders.view`, `orders.fulfil`, `orders.return`, `stock.view`) and **Inspector** (`orders.view`, `orders.inspect`, `stock.view`, `stock.adjust`). All non-locked, so store admins can customise them; `Store::ensureDefaultRoles()` is idempotent and only writes permissions when the role is new or locked. Existing Manager/Viewer roles are untouched because `orders.manage` is treated as implying all four department keys.
- **Order workflow services (Phase 3, 2026-07-24):** `App\Services\Orders\` holds three classes. **`OrderWorkflowService::transition(Order|PosOrder, FulfillmentStatus $target, ?User $actor, ?string $reason)`** is the ONLY way fulfillment status changes — the board, the WhatsApp webhook and the returns flow all call it. It re-reads the row under `lockForUpdate()` inside a transaction (without it, two staff clicking "Confirm" simultaneously both pass the legality check and stock is deducted twice), validates the edge + the reason, applies stock effects, projects the legacy `status`, opens the OrderReturn when target is `Returned`, and writes a spatie activity entry (`event('fulfillment_transition')`, properties from/to/reason). Throws `ValidationException` — controllers catch it and `back()->with('error', ...)` because `SaasLayout`'s ToastNotification renders `flash.error` (an Inertia request is not JSON, so a raw 422 would show the user nothing). **`StockMovementWriter::move()`** is the single place stock quantities are mutated by the lifecycle: locks the Stock row, writes a `StockLedger` row always, and an `InventoryAdjustment` + `SyncInventoryToWebhooks` dispatch ONLY when `$warehouse->isSellable()`. **`ReturnInspectionService`** does open/startInspection/disposition/close/outcomeSummary. `App\Support\OrderLineItems::for()` normalises POS rows and the online JSON blob into one shape with `product_id` (nullable — an unmatched online line is inspectable but moves no stock); `OrderPresenter` still does the same for display.
- **Container cycle to avoid: OrderWorkflowService ↔ ReturnInspectionService.** The workflow service takes ReturnInspectionService in its constructor (to open a return on the `Returned` transition), so ReturnInspectionService must NOT constructor-inject OrderWorkflowService — it resolves it lazily with `app(OrderWorkflowService::class)` inside `advanceOrder()`. Injecting both ways deadlocks the container.
- **`stockIsCommitted()` is what makes one code path serve both channels:** returns false for `Cancelled`, true for any `PosOrder` (POS deducts at checkout for instant AND delivery), and `status !== Pending` for `Order`. `applyStockEffects()` then just diffs before/after — commit (−qty, ledger `sale`) when it flips false→true, release (+qty, ledger `adjustment`) when true→false. That single rule gives: online confirm deducts, POS confirm is a no-op, and cancelling a POS delivery order still gives the units back.
- **`Order::markAsConfirmed()` / `markAsCancelled()` now route through the workflow service (2026-07-24):** they guard with `canTransitionTo()` first (so an order staff already advanced doesn't throw), transition, then stamp `whatsapp_confirmed_at`/`whatsapp_cancelled_at` regardless. Effect: a customer replying YES on WhatsApp commits stock and lands the order in the fulfillment lane, so the confirmation queue drains itself and staff only handle non-responders.
- **Order permissions are per-department with a coarse override (2026-07-24):** `PermissionCatalog` gained `orders.confirm`, `orders.fulfil`, `orders.return`, `orders.inspect`. `OrderController@updateStatus` allows the move when the user has `$target->permission($current)` **OR** `orders.manage` — the coarse key implies all four so existing Manager/Viewer roles keep working unchanged. The dedicated roles (Confirmation agent / Warehouse / Inspector) are step 7, not yet seeded. Returns routes live under `/dashboard/orders/returns` (`dashboard.orders.returns.*`) and are declared BEFORE `/{order}` so "returns" isn't swallowed by the order show route; the write actions carry `perm:orders.inspect`.
- **Returns are item-level, never order-level (2026-07-24):** `order_returns` (header: store, polymorphic `returnable` = Order|PosOrder, `reference` RET-YYYYMMDD-0001 unique per store, status awaiting_inspection|inspecting|closed, `reason`) + `order_return_items` (per line: `quantity_returned`, `condition` resellable|damaged|missing, `destination_warehouse_id`, `stock_ledger_id`, `refund_amount`). A 3-line order can come back 2 resellable + 1 damaged — an order status can never express that, so `fulfillment_status` is a ROLLUP of these rows. `order_return_items.stock_ledger_id` is the idempotency guard: the disposition service skips any line that already has one, so a double-submitted inspection form can't restock twice (`hasStockMovement()` vs `isDispositioned()` — the former is the stock guard, the latter just means the inspector ruled).
- **Stock NEVER moves when an order is flagged `returned` — only at inspection disposition.** The goods are unverified until an inspector physically handles them; restocking on the flag is how phantom inventory gets created. Resellable → primary warehouse + `stock_ledger.type='return'` + an `InventoryAdjustment` (so the storefront learns it's sellable again). Damaged → damaged warehouse + `type='damage'` + **NO** InventoryAdjustment (pushing it would advertise written-off units). Missing → no stock movement at all. Online orders commit stock at `Pending → Confirmed`; POS already deducted at checkout, so that step is a no-op for `PosOrder` (guard on `$order instanceof Order`).
- **Damaged stock = a warehouse with `type='damaged'`, NOT a `stocks.condition` column (2026-07-24):** `warehouses.type` is `standard|damaged|quarantine` (`Warehouse::TYPE_*` constants + `scopeSellable()` + `isSellable()`). Chosen because damaged units stay ordinary `Stock` rows, so the `(product_id, variant_id, warehouse_id)` unique key, StockLedger, and transfers all work untouched; a `condition` column would have broken the unique index and needed a filter on every existing stock query. `Store::getDamagedWarehouse()` lazily creates+attaches it (`is_primary=false`, priority 99) — mirrors `getPrimaryWarehouse()`, never returns null. **The trade-off: anything summing stock must now exclude it.** Use `Product::scopeWithSellableStock()` (adds BOTH `total_stock` = standard-only and `damaged_stock`) instead of a bare `withSum('stocks as total_stock','quantity')` — all 4 call sites (DashboardController, ProductController, StockController ×2) were converted. Also scoped: `Product::sellableStocks()` relation, `Product::getTotalStock()`/`getTotalVariantStock()` (unscoped when no warehouse id is passed, exact when one is), `Store::getTotalStockValue()` (joins warehouses), and `SyncInventoryToWebhooks` — the last one now computes `new_stock` as the SUM across sellable warehouses via `sellableStock()` rather than reading `adjustment->quantity_after` (which was only ever one warehouse's balance).
- **POS delivery BYPASSES the confirmation desk (rule change 2026-07-25):** `FulfillmentType::initialFulfillmentStatus()` for Delivery now returns `FulfillmentStatus::Confirmed` (was `Pending`). Rationale: a cashier pre-approves a POS delivery order face-to-face, so it must skip the Confirmation department and drop straight into the **packing** queue (Confirmed is in the `fulfillment` phase). Only ONLINE orders (`Order` model) still start at `Pending`/confirmation. The channel `status` column is UNCHANGED — still `pending_delivery` — because `OrderPresenter::pos()` derives the "delivery" source lane from it; so a POS delivery order reads `source='delivery'` + `phase='fulfillment'` simultaneously. Backfill migration `2026_07_25_120000` moved existing `pos_orders` at (`status='pending_delivery'` AND `fulfillment_status='pending'`) → `confirmed` (safe: POS stock is committed at checkout regardless, so no workflow side-effect is skipped). Tests: `tests/Feature/Orders/PosDeliveryRoutingTest.php` (5, incl. asserting it appears in `/dashboard/departments/packing` with 1 row and `/confirmation` with 0). NO frontend change needed — the packing queue already filters by fulfillment phase.
- **POS fulfillment type → instant vs delivery flow (Phase 3, 2026-07-24; delivery routing amended 2026-07-25):** `pos_orders` carries TWO status columns: `status` (channel/original state string: `completed` | `pending_delivery` | `cancelled`) and `fulfillment_status` (cast to `FulfillmentStatus` enum, drives the unified Order Management board). `OrderPresenter::pos()` routes `status === 'pending_delivery'` into the **delivery** source lane; everything else is `pos` (Direct POS). The `App\Enums\FulfillmentType` enum (`instant`|`delivery`) is the single source of truth mapping checkout choice → both columns: instant → status `completed` + fulfillment `Completed`; delivery → status `pending_delivery` + fulfillment **`Confirmed`** (+ `fulfillment_updated_at = now()`) — see the bypass note above; it was `Pending` until 2026-07-25. Data flow: useCart (`fulfillmentType`/`deliveryAddress` + `SET_FULFILLMENT`/`setFulfillment`) → Checkout.jsx toggle (Instant/Delivery, delivery reveals required address) → CheckoutPreviewModal badge (button reads "Validate & Queue" for delivery) → Dashboard payload (`fulfillment_type`/`delivery_address`) → CheckoutController validation (`Rule::enum(FulfillmentType)`, `required_if:fulfillment_type,delivery` for address) → OrderProcessingService sets both status columns from `FulfillmentType::tryFrom()`. **Inventory is deducted immediately for BOTH types** (the sale commits/reserves the goods so they can't be oversold) — `CheckoutController` always calls `adjustInventory()`; the delivery difference is purely the fulfillment STATE, not stock timing. `delivery_address` column added by migration `2026_07_24_120000` (nullable text, only populated for delivery orders). Frontend gotcha: Dashboard `submitCheckout` skips `setShowInvoice(true)` when `res.data.is_delivery` (delivery orders queue silently, cashier can Re-print a slip); the success banner text also branches on `is_delivery`.
- **PosOrder URL/route binding:** `PosOrder::getRouteKeyName()` returns `receipt_number` (e.g. `ANIQ-20260712-0001`), so `/dashboard/orders/{order}` uses the receipt number, not the ULID. `resolveRouteBinding()` accepts EITHER `receipt_number` OR the `id`, so older id-based links (e.g. FacturesDetail "View POS order" via `facture.pos_order_id`) still resolve. When building POS order links in JSX, prefer `o.receipt_number`. Gotcha history: `invoiceReference()` (Invoiceable) also `return (string) $this->receipt_number` — do NOT confuse it with `getRouteKeyName()`. Tenant scoping (BelongsToTenant) still applies during binding, so a receipt number only resolves within the active store.
- **Invoice email is synchronous by design:** `InvoiceController::email` uses `Mail::to()->send()` (NOT `->queue()`) inside try/catch, and only calls `InvoiceService::markSent()` after the mailer accepts the message. Rationale: `QUEUE_CONNECTION=database` means `queue()` returns before delivery, so marking "sent" then would lie if the job later fails (and with no worker running, nothing sends at all). ## Key Learnings (continued)

- **(2026-08-19) "Can't show two contradictory states at once" bugs are almost always a two-sources-of-truth problem, on both ends.** The Shopify verification panel showing green+red simultaneously had a backend half (a status-setting function ran before all the checks that could invalidate it were done, and nothing corrected it afterward) and a frontend half (the badge and the error message were rendered from two independently-updated pieces of state — persisted `connection` props vs. an ephemeral just-fetched `testResult`). Fixing only one half leaves the bug reproducible from the other angle. The durable fix on the frontend side is to collapse to ONE computed variable (`state = 'connected' | 'failed' | 'untested'`) that every rendered piece (badge, color, message) reads from — never let two DOM elements draw from two different state variables when they're supposed to describe the same fact. On the backend side: audit every early-return/exit path of a multi-step verification function and make sure each one persists its own final status — not just the ones added most recently.

- **(2026-08-19) `ShopifyConnector::client()` was sending `Authorization: Bearer {token}` — Shopify's Admin REST API only accepts `X-Shopify-Access-Token`.** Found while implementing the client-credentials refactor (task explicitly called out "Do not use Authorization: Bearer" as an anti-pattern to avoid), but this bug predates that task and affected **every** existing Shopify connection, not just the new method — it directly explains a real production log the user pasted in (`"Authentication failed for shopify"` / `guard()` throwing on a 401 during a product sync, timestamp 2026-08-19 15:57). Fixed in `ShopifyConnector::client()` for both the legacy `admin_token` (pasted-token) method and the new `admin_client_credentials` method — a pure header-correctness fix, not new behavior. Cross-check: `SyncInventoryToWebhooks::syncToShopify()` (a separate, unrelated call site) already used the correct `X-Shopify-Access-Token` header, so the bug was isolated to the connector's shared `client()` builder. **Lesson: when a user pastes an error log alongside a task, always check whether it's explained by something the task is already about to touch — it very often is.**
- **(2026-08-19) Shopify Dev Dashboard app credentials: `client_id`/`client_secret` → Admin API token is the `client_credentials` OAuth grant, not app install OAuth.** `POST https://{shop}.myshopify.com/admin/oauth/access_token` (form-encoded: `grant_type=client_credentials`, `client_id`, `client_secret`) returns `{access_token, scope, expires_in}` — a short-lived token, never the long-lived install-flow token. `App\Services\Shopify\ShopifyAuthService` generates + caches it (`Cache` key `shopify:connection:{id}:admin_token`, TTL `expires_in - 300s`), reusing the *already-encrypted* `PlatformConnection.consumer_secret` column for `client_secret` and the plain `consumer_key` column for `client_id` — no migration needed, those columns already existed for WooCommerce's API key/secret and were sitting unused for Shopify. The generated token itself is **never** written to `PlatformConnection.access_token` — only ever cached. `ShopifyConnector::client()` resolves the token source by `connection_method` (`admin_client_credentials` → `ShopifyAuthService::getToken()`; legacy `admin_token` → the raw DB column, unchanged) — fully transparent to `ProductSyncService`/`ProductPushService`, neither needed a single line changed since both go through `ConnectorFactory`/`new ShopifyConnector($connection)` and never touch `access_token` directly.

- **(2026-08-19) Correction to the "`Stock::saved()` is always inventory-engine-safe" note above: safe for the ledger/balance, but NEVER triggers outbound platform sync.** `InventoryCompatibilityBridge::fromLegacyStock()` calls `InventoryEngine::setOnHand(..., queueSync: false)` explicitly (`app/Services/Inventory/InventoryCompatibilityBridge.php:25`) — by design, so pulling a product FROM WooCommerce doesn't immediately bounce back OUT to WooCommerce. `InventoryEngine::mutate()`'s `queueSync()` (which dispatches `SyncInventoryToWebhooks`, the only thing that ever notifies a platform of a stock change) only fires when `$queueSync` is left at its default `true` — i.e. only for a *direct* `InventoryEngine::setOnHand()/adjustOnHand()` call, never for a write that arrives via the legacy `Stock` table. This is exactly why the Product Edit page's old "write `product.qty` → `Stock::updateOrCreate()`" flow could never reach WooCommerce even in principle, regardless of any connector bug — fixed by adding `ProductController::adjustStock()`, which calls `InventoryEngine` directly. - **(2026-08-19) `ProductPushService`/`WooCommerceConnector`/`ShopifyConnector` already carry far more outbound capability than what's actually invoked — always check whether the method you're about to write already exists as dead code before writing it.** `WooCommerceConnector::pushProductVariant()` (and its Shopify equivalent) already existed, fully correct (`PUT /products/{parent}/variations/{variation}` using `ProductVariantChannelListing`'s remote id) — `ProductPushService::pushProduct()` just never called it, so a variable product's per-variant field edits (sku/price) never reached WooCommerce even though the plumbing was there. - **(2026-08-19) Shopify webhook payload shape === one item from the connector's own REST list response.** `App\Connectors\ShopifyConnector::parseProduct()`/`parseOrder()` (both `protected`) already parse the exact JSON shape Shopify POSTs for `products/create|update`/`orders/create|updated` webhooks — a webhook body IS one raw resource object, byte-identical in shape to one element of `GET /products.json`/`GET /orders.json`. - **(2026-08-19) A guest/webhook route can NEVER use implicit route-model binding on a `BelongsToTenant` model.** `TenantScope` (global scope from `App\Models\Concerns\BelongsToTenant`) filters queries by the *authenticated* tenant context (`App\Support\TenantContext`) — a webhook POST has no session/auth, so `TenantContext` is empty and implicit `{connection}` → `PlatformConnection` binding would silently fail to find a real row (or worse, behave inconsistently). - **(2026-08-19) `$request->validate()` omits a `nullable` key from its return array entirely when the request doesn't send that key at all — it is NOT set to `null`.** Reading `$validated['optional_field']` directly (no `??`) throws `Undefined array key`. This only surfaces when a caller omits the key outright (a raw API call, a Pest test posting a minimal payload) — a browser form built with `useForm()` that initializes every field to `''` always sends the key, masking the bug in normal use. Any controller doing `$validated['x']` on a `nullable` rule should use `$validated['x'] ?? null` (or `?? default`). Found in `ProductController::store()/update()`, fixed. Worth grepping other controllers with the same `$validated['optional...']` pattern if this class of bug matters — not yet audited elsewhere.
