## Key Learnings

- **Global UI consistency pass (2026-08-28) + a real gotcha with forked sub-agents doing parallel page-level edits:** When dispatching 4 parallel `fork` agents (each scoped to a disjoint set of page files: Products/Inventory, Delivery/Fulfillment, Integrations, Settings/Dashboard) to apply the same token-conversion pattern established in the Orders/Appearance sessions, one fork's final report came back describing itself as having "dispatched forks" and coordinating with "other agents" — i.e. it briefly lost track of being one of the forks and thought it was the orchestrator, because a fork inherits the FULL parent conversation history, including the parent's own `Agent` tool calls that spawned it and its siblings. That confusion led it to spawn its own nested sub-agents (visible as extra, unexpected task-ids beyond the original 4), which piled onto the same session/rate budget and contributed to all 4 runs eventually failing with a session-limit error partway through. **Lesson: when forking multiple agents in parallel for scoped, mechanical edit work, verify each fork's actual file diffs directly (`git diff`/`git status` on its assigned files) rather than trusting its self-reported summary — a confused summary does not necessarily mean the underlying edits are bad (in this case they were all still correct, just incompletely finished), but it does mean the report format/completeness can't be trusted.** After the failure, remaining work was finished by direct sequential edits (no further forking) rather than re-dispatching agents, both to stay within budget and because per-file `git diff --stat` review (balanced insertion/deletion counts, e.g. `Dashboard/Index.jsx` at 36/36) proved to be a fast, reliable way to confirm a batch's edits were pure class-string swaps with zero structural/logic changes before trusting it.
- **Established token-conversion vocabulary for this pass** (reusable verbatim on any future page in this app still on the old theme): `bg-indigo-600 text-white hover:bg-indigo-500` (or `bg-blue-600 ...`) → `bg-primary text-primary-contrast hover:bg-primary-strong`; `focus:ring-indigo-500`/`border-indigo-500` (active/selected state) → `focus:ring-primary`/`border-primary`; `text-red-600 dark:text-red-400` → `text-danger`; `text-amber-600 dark:text-amber-400`/`text-amber-700 dark:text-amber-300` → `text-warning`; `text-emerald-600 dark:text-emerald-400`/`text-emerald-700 dark:text-emerald-300` → `text-success`; the compound tinted-banner pattern `bg-{color}-500/10 border-{color}-500/30 text-{color}-700 dark:text-{color}-300` → `bg-{success|warning|danger}-soft border-{token}/30 text-{token}`; bare `rounded-lg` (buttons/inputs/pills) → `rounded-[var(--radius-button)]`; bare `rounded-xl`/`rounded-2xl` (cards/modals/panels) → `rounded-[var(--radius-card)]`. **Deliberately left alone, per established precedent**: per-provider brand-identity colors (Shopify/WooCommerce/YouCan/Ozon/Sendit icon gradients in `Integrations/Index.jsx`'s `ICONS` map — these mirror each platform's own real brand color, not our app's brand), purely informational/categorical hues unrelated to brand or success/warning/danger (e.g. `StatusBadge`'s blue/indigo/cyan info states, `SOURCE_TONE` POS-vs-Online badges, sibling department pages' `tone: 'indigo'` "in-progress" stat tiles in `QueueParts.jsx`'s `TONES` map — kept consistent across `Packing.jsx`/`Confirmation.jsx`/`WaitingForStock.jsx`/`Picking.jsx` rather than converting just one to `primary` and leaving the others mismatched), and avatar/identity gradients (`UserDropdown`/`StoreSwitcher`).

- **DANGER — mutating a model's relation, then later calling anything that `$model->load(...)` in the SAME array literal, silently discards the mutation (2026-08-20 follow-up 5):** `Inertia::render('...', ['product' => $product, 'readiness' => $readiness->check($product)])` looks harmless, but PHP evaluates array values left-to-right and 'product' => $product stores an OBJECT REFERENCE, not a snapshot. `ProductPublishReadinessService::check()` internally calls `ProductOptionSnapshot::build($product)`, which does `$product->load(['variants.attributeValues' => ..., 'variants.attributeValues.attribute'])` — this REPLACES the `variants` relation with a freshly-queried collection of BRAND NEW `ProductVariant` instances. Any props set on the OLD variant instances via `$product->variants->each(fn($v) => $v->someProp = ...)` BEFORE that point are silently gone, because 'product' in the array still points to the same `$product` object, whose `variants` relation just got swapped out from under it. This bit `ProductController@edit`'s new per-variant stock props (`stock_on_hand` etc., see below) — they were being set correctly (confirmed via `Log::debug` dump immediately after the mutation) but vanished by the time the Inertia response was inspected. **Fix pattern: compute anything that might reload a relation (readiness checks, snapshot builders, any service call that takes the model) FIRST, store the result in a local variable, THEN do relation-mutating work, THEN build the response array from the pre-computed values** — never call such a service inline as a later array value after mutating relations on that same model earlier in the same statement/request. General lesson: `$product->load(x)` deep in a seemingly-read-only "check"/"snapshot" service is a real hazard for any caller who mutated `$product`'s relations first and expects those mutations to survive.

[2026-08-24] **Never name a controller helper `authorize()` in a class extending `App\Http\Controllers\Controller`** — it already uses `AuthorizesRequests`, which declares a public `authorize($ability, $arguments)`. Redeclaring it with a different (e.g. private) signature is a PHP fatal visibility-collision at class-load time, and because PHP only autoloads a class on first reference, the crash doesn't happen at bootstrap — it happens the moment a route actually resolves that controller, producing a completely silent process crash (zero stdout/stderr, exit code 2) that looks like a broken test harness rather than a PHP error. See [[bug-delivery-note-controller-authorize-method-collision]]. Also: **never `->sync()`/`attach()` a `belongsToMany` whose pivot table has its own ULID primary key** — those write raw rows via the query builder and skip `HasUlids`' `creating()` hook, leaving `id` null against a NOT NULL PK. Create the pivot model directly (`PivotModel::firstOrCreate([...])`) instead. See [[bug-delivery-note-shipments-pivot-ulid-null-via-sync]].

[2026-08-24] **Confirms the 2026-07-26 lesson below, again:** when a test fails and you suspect "did MY change cause this", `git stash` is the WRONG tool if the working tree already has other uncommitted changes from prior work — it reverts everything back to the last commit, not just your own edits, so a stash-and-rerun answers "does ANY uncommitted work cause this", not "did I cause this". Diagnosed correctly here by reading the actual `git diff` of the file in question instead: two failing tests (`OrderChannelViewsTest`'s 403→404 tenant-scope check, `OrderDepartmentsTest`'s confirmation claim-gate) turned out to be pre-existing bugs already present in the user's own uncommitted WIP on `OrderController::updateStatus`/`showOnline` — unrelated to and unmodified by the delivery-provider work, confirmed by reading the diff hunks around my own (additive-only) edits rather than trusting the stash result.

[2026-07-26] **`$table->unique([col_a, col_b])` on tables/columns with long names silently overflows MySQL's 64-char identifier limit** (error 1059) — and it aborts `migrate:fresh` mid-run, leaving every later migration Pending (that is exactly how the pre-squash chain was broken: it died at `product_variant_attribute_values` and 38 migrations never ran, while SQLite — which allows long index names — hid it in tests). ## Key Learnings (continued)

- **(2026-08-19) "Can't show two contradictory states at once" bugs are almost always a two-sources-of-truth problem, on both ends.** The Shopify verification panel showing green+red simultaneously had a backend half (a status-setting function ran before all the checks that could invalidate it were done, and nothing corrected it afterward) and a frontend half (the badge and the error message were rendered from two independently-updated pieces of state — persisted `connection` props vs. an ephemeral just-fetched `testResult`). Fixing only one half leaves the bug reproducible from the other angle. The durable fix on the frontend side is to collapse to ONE computed variable (`state = 'connected' | 'failed' | 'untested'`) that every rendered piece (badge, color, message) reads from — never let two DOM elements draw from two different state variables when they're supposed to describe the same fact. On the backend side: audit every early-return/exit path of a multi-step verification function and make sure each one persists its own final status — not just the ones added most recently.

- **(2026-08-25) `Http::fake([...])` only ever matches the FIRST-registered rule for a given URL pattern within one test — a LATER `Http::fake([...])` call in the same test body can never override an earlier one for an overlapping pattern.** Confirmed by reading `Illuminate\Http\Client\Factory::fake()`/`stubUrl()` source directly: each call APPENDS to `$this->stubCallbacks` (never resets it), and resolution iterates in registration order, using the first match. **Consequence for any test needing a stub's response to CHANGE across two calls to the same endpoint within one test** (e.g. "first send is unconfirmed, a retry action is confirmed"): register ONE stub as a closure that changes its return value based on an invocation counter (`$calls++`), never two separate `Http::fake()` calls — the second one is silently ignored for that URL pattern. - **GOTCHA — Carbon 3's `diffInSeconds()` (and the other `diffIn*` methods) default to a SIGNED result; Carbon 2 defaulted to absolute.** `$end->diffInSeconds($start)` now returns negative when `$end` is after `$start` (this project is on `nesbot/carbon` 3.11). - **GOTCHA — PHP's `json_encode()` drops the decimal point on a whole-number float by default** (`json_encode(80.0)` → `"80"`, which decodes back as `int(80)`, not `float(80.0)`) — `JSON_PRESERVE_ZERO_FRACTION` is required to round-trip it as a float, and Inertia's response encoding doesn't set that flag. Any Pest `assertInertia()->where('some.float_prop', 80.0)` assertion will fail with "80 is identical to 80.0" whenever the real value happens to be a whole number. Fix in the TEST (not the service): compare with a closure, `->where('key', fn ($v) => (float) $v === 80.0)`, rather than asserting an exact float literal.

- **GOTCHA — SQLite (used for this project's Pest test DB) rejects `HAVING` that references a SELECT-list alias when there's no `GROUP BY`, even though MySQL accepts it** (`"HAVING clause on a non-aggregate query"`). `Product::scopeWithSellableStock()` (`app/Models/Product.php`) adds `total_stock`/`damaged_stock` as correlated scalar subqueries (verified via `->toSql()` — NOT a join+group-by), so filtering low-stock products at the DB level via `havingRaw('COALESCE(total_stock,0) <= ?', ...)` needed an explicit `->groupBy('products.id')` added first to satisfy SQLite — harmless since `id` is already unique per row, so grouping changes nothing about which rows match. `->count()` on a query with `groupBy`+`having` was empirically verified (via tinker) to correctly return a scalar count on both engines, not just row-fetch-then-PHP-count. This DB-level filter avoids loading the whole product catalog into memory just to compute `total_products`/`low_stock_count`/`low_stock_products` (previous code did `Product::withSellableStock()->get()` unconditionally, then filtered in PHP) — `total_products` itself needs no `withSellableStock()` at all, a plain `count()` suffices.
- **Order-action authorization UX (2026-08-28): the "blank 403 page" bug was Inertia's built-in error MODAL, not a full navigation.** `router.post()` on a response with no `X-Inertia` response header (the default for an uncaught `abort_unless(...,403,$msg)`) makes `@inertiajs/core` fire an `invalid` event and, if uncancelled, show its OWN full-screen modal with the raw error HTML in an iframe (`node_modules/@inertiajs/core/dist/index.esm.js`'s `handleNonInertiaResponse()`/`modal_default.show()`) — visually identical to "navigated to a blank page" but not an actual page navigation. Fixed via `bootstrap/app.php`'s `$exceptions->respond()` → `App\Support\InertiaErrorResponder::respond()`, which is intentionally NOT a blanket "convert every 403 into a redirect" — it is gated on `$request->header('X-Inertia') && !$request->isMethod('GET')` (i.e. a genuine SPA action click, never a plain HTTP/Pest request), because ~10+ existing tests across the suite (`ConfirmationDeskClaimTest`, `OrderDepartmentsTest`, `OrderChannelViewsTest`, etc.) assert `->assertForbidden()` on POST routes and would break if the status code ever changed. Only a real Inertia action gets `back()->with('error', $message)`; the exact same route hit without that header keeps the byte-for-byte original 403 response. A full-page GET on 403/404/419/500 instead renders `Inertia::render('Error', [...])->toResponse($request)->setStatusCode($status)` — same trick: status code is ALWAYS preserved, only the response BODY changes, so `assertForbidden()`/`assertNotFound()` (which only check status) never break anywhere in the suite.
- **GOTCHA: `TestCase::withHeaders([...])` persists across every later request in the same test method — it does NOT scope to one call.** A test doing `$this->withHeaders(['X-Inertia' => 'true'])->post(...)` then a plain `->get(...)` later in the SAME test still carries `X-Inertia: true` on that second call, which trips Inertia's own version-mismatch guard (`Inertia\Middleware::handle()` line ~149: a GET request carrying `X-Inertia` gets a 409 unless `X-Inertia-Version` matches `Inertia::getVersion()`, which a test can't easily pre-compute since the version closure is only registered by the middleware during actual request handling). Fix: pass headers as the per-call 3rd argument instead — `$this->post($uri, $data, ['X-Inertia' => 'true'])` — which does NOT leak into subsequent calls on the same `$this`.
